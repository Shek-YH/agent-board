## 项目是什么

一个纯本地 Node.js 服务，实时汇总 8 个 AI 编程/办公 Agent（Claude Code / Codex / Pi / DeepSeek Harness / WorkBuddy / ZCode / Marvis / 豆包）的会话记录到一个看板，并且能一键检测/安装这些 Agent。零 npm 依赖，Node 内置 `http` + SSE，前端原生 JS 无构建工具。跑在 `http://127.0.0.1:4876`。

详细功能清单、目录结构、启动方式见 [README.md](../README.md)。

## 这个项目的开发流程约定（建议继续遵守，即使你没有对应的技能/插件）

之前的开发流程是：**brainstorm（问清楚需求，提出方案，等用户确认）→ 写设计文档到 `docs/superpowers/specs/` → 写实现计划到 `docs/superpowers/plans/`（拆成小任务，每个任务写清楚要改的文件、before/after 代码、验证步骤）→ 按任务逐个实现，每个任务走 TDD（先写测试，确认失败，再写实现代码，确认通过）→ 提交**。这套流程背后没有依赖任何专属工具，就是纪律问题，你完全可以手动照做，不需要有相同的插件。

代码审查方面：之前每个任务实现完之后会做两轮审查——先检查是否符合规格（有没有多做/少做），再检查代码质量（有没有 bug、边界情况、风格问题）。你可以自己审查自己的代码，或者如果你的工具支持子代理/多轮自我审查，也可以照搬这个两阶段模式。**不要跳过审查直接提交**，之前审查阶段发现过好几个真实 bug（比如一个"点击安装"按钮的事件绑定错误，会导致缓存对每次点击都失效）。

git 提交：小步提交，每个任务一个 commit，message 用中文说清楚改了什么、为什么。**不要 `git push`**（没配置 remote，也没人要求你配）。

## 环境专属的坑（这是最容易在交接中丢失的知识，务必仔细看）

1. **这台 Windows 机器的 Bash-工具 `cmd.exe` 环境 PATH 是残缺的**（缺 `%LOCALAPPDATA%\Microsoft\WindowsApps`），会导致 `winget` 之类的命令"查不到"，但其实是真实存在的——只是这个特定 shell 环境找不到。如果你的工具里同时有 Bash 和 PowerShell 两种终端能力，验证 `winget`/需要用户级 PATH 的命令时优先用 PowerShell，不要因为 Bash 里查不到就下"这个命令不存在"的结论。

2. **`node --test` 不能带路径参数**。`node --test` 可以，`node --test lib/` 会抛 `MODULE_NOT_FOUND`（这个 Node/Windows 组合的已知怪癖）。

3. **`server.js` 是一个常驻进程，被 `agent-board-watchdog.js` 看护**，跑在 `127.0.0.1:4876`，是用户真实在用的看板，不是一次性测试实例：
   - 看门狗每 30 秒 ping 一次 `/api/state`，连续 2 次失败（约 60 秒）才会拉起新进程，新进程启动还要再等一会，全程约 60-70 秒
   - 你改了 `server.js` 的代码后，**必须手动重启这个进程新代码才会生效**（前端静态文件 `public/app.js` 不用重启，每次请求都是现读的）
   - 重启方法：用 `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*server.js*' }` 精确找到 `server.js` 自己的进程 PID（不是看门狗的 PID，两者都是 `node.exe` 名字一样，必须按 CommandLine 区分），只 `Stop-Process` 这一个，等看门狗自动拉起新的
   - **绝对不要碰看门狗自己的进程**（`agent-board-watchdog.js`），也不要用 `taskkill /IM node.exe` 这种会一次杀掉所有 node 进程的命令——这台机器上同时跑着很多其他 node 进程（MCP servers、其他工具），杀错了影响面很大

4. **`~/.agent-board/tool-paths.json`**（即 `%USERPROFILE%\.agent-board\tool-paths.json`）是用户手动配置的路径覆盖文件，修复了这台机器 Node 装在非标准路径（`D:\Program Files\node-v22.14.0-win-x64\node_global\`）导致的探测失败问题。**如果你需要临时修改这个文件做测试，用完必须原样恢复**，并且：**不要用 Bash 工具的 `node -e "..."` 内嵌 Windows 路径的写法去写这个文件**——反斜杠转义在 git-bash 环境里传递时会被破坏（真实发生过，4 个反斜杠丢了 2 个，导致路径损坏）。正确做法：直接用你工具里"写文件"的能力（不经过 shell 参数传递）写入完整 JSON 内容，写完读回来验证一字不差。

5. **workbuddy 疑似是这台机器工具链本身的一部分**（进程列表里能看到 `.workbuddy` 目录下的常驻进程）。**不要真的卸载 workbuddy 做测试**，风险和收益不成比例。同理，claude/codex/deepseek 这几个命令行工具本身可能也是当前正在用来跑你（新 agent）的工具链的一部分——动手卸载/覆盖之前先确认清楚,不确定就问用户。

6. **这台机器上 8 个 agent 目前全部处于"已安装"状态**（截至 2026-08-23），gui 类工具（workbuddy/zcode/marvis/doubao）的探测方式是 registry/path 扫描，**没有类似 tool-paths.json 那样的覆盖机制能伪造"未安装"状态**。如果需要测试"未安装"相关的 UI 分支，要么找机器上真的没装的工具，要么就事先跟用户说明白"没法在这台机器上安全地伪造这个状态，只能做到数据层面验证 + 代码审查"，不要为了测试去真的删除用户的真实应用数据。

7. **豆包（doubao）被用户明确要求排除出所有未来开发范围**。这不是"暂缓"，是长期决定。探测代码保留，但不要给它加任何新功能（安装引擎等）。

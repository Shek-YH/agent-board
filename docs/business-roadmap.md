## Context（现状与问题，写于 2026-08-22，部分已过时——见文末"更新记录"）

看板项目本质是一个**纯本地 Node.js 服务**：

- `server.js` 起一个本地 HTTP 服务（默认 `127.0.0.1:4876`）
- `lib/store.js`（JSON 落盘）+ `lib/watcher.js`（监听各 AI 工具的本地会话目录）
- `lib/adapters/` 下 8 个适配器（claude/codex/workbuddy/deepseek/doubao/marvis/zcode/pi）
- 前端是 `public/index.html` + `public/app.js` 的原生页面，没有构建工具
- 启动方式是 `.bat`/`.vbs`（面向 Windows 单机、开机自启场景）
- 最初没有设置面板、账号体系、鉴权或 license 相关代码

补充几个探索后发现、会直接影响后面选型的细节：

- **零 npm 依赖、纯 Node 原生 `http` + SSE 推送**：改造成本可控，但意味着没有任何框架帮你处理鉴权/路由。
- **数据落盘用 JSON 文件**（`%LOCALAPPDATA%\AgentBoard\data.json`），`lib/store-sqlite.js` 是**弃用**方案——当初改用 SQLite 后被 **360 安全软件误判、锁库文件**，退回 JSON。这类工具打包分发后极容易被国内杀软/Defender 误报，打包分发前必须把"过 AV 白名单"当成硬需求。
- **窗口激活用运行时编译的 C# DLL**：`server.js` 里内嵌 C# 源码，通过 PowerShell `Add-Type` 运行时编译成 Win32 DLL。这个模式是杀软/SmartScreen 重点关注的特征之一，打包分发前建议改成构建期预编译好 DLL 随包分发，配合代码签名。
- 8 个 Agent 的适配器目前是**硬编码**在 `AGENT_DEFS` + 各自适配器文件，新增靠改代码，不是运行时插件。
- 项目目前没有推到远程仓库，只有本地 commit（截至 2026-08-23 已有 80+ 次本地提交，仍未配置 remote）。

参考调研：EchoBird（`github.com/edison7009/EchoBird`）用 Tauri + Rust，应用管理模块的思路是"为每个受支持工具编写本地配置描述文件，检测/安装/修复它"——这一思路已经被本项目借鉴并落地（见"更新记录"）。

### 阶段 1：安装体验 —— 自动检测 + 按需安装（**已完成**）

原计划的四个子项：
1. 探测层：把每个 Agent 的"数据在哪、装没装"信息拆成独立描述文件 —— **已实现**：`lib/adapters/*.js` 里的 `detect` 对象（`probe`/`install`/`network`/`afterInstall`）
2. 首次安装向导 —— **未做成独立向导**，但"应用管理"弹窗已经等效覆盖了这个需求
3. 设置面板里的应用管理（参考 EchoBird） —— **已实现**：`GET /api/agents/status`、`POST /api/agents/:id/install`，前端"应用管理"弹窗
4. 依赖自动检测 —— **已实现**：`installAgent()` 的 Node 版本检查、被墙地区检查

### 阶段 2：分发形态 —— Web / Electron / 其他（**未开始**）

现状仍是"本地 Node 服务 + 浏览器打开网页"。原文档的对比表和推荐路径：

| 形态 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|
| 保持 Web(本地 Node 服务) | 改造成本最低，跨平台 | 用户需要自己装 Node；本地敏感数据以明文网页方式暴露；难做强鉴权 | 不打算防盗版、目标用户是愿意折腾的开发者 |
| Electron 打包 | 双击就能用，托盘/自启动/原生通知 | 包体积大、内存占用高、混淆需求高 | 卖给不太懂技术的团队 |
| Tauri（Rust 壳） | 包体积小、逆向门槛高（正是 EchoBird 的选择） | 需要把关键逻辑用 Rust 重写 | 认真做付费桌面产品、愿意为防破解投入 Rust 改造 |

推荐路径：先包一层 Electron（工作量最小），鉴权校验单独用 Rust/Go 写成本地校验子进程或放服务端校验（见阶段 3），核心业务逻辑先不用完全重写。

### 阶段 3：鉴权与计费（**未开始**）

结论：对单机小工具，"防止 100% 被破解"投入产出比很低，合理目标是"让破解门槛高于大多数用户愿意折腾的程度"。

1. **账号 + 云端订阅校验（推荐主方案）**：登录一个极简账号，本地客户端启动时向服务端换取短期 token（24-72 小时），本地凭 token 解锁付费功能；离线宽限期内用缓存 token。
2. **离线 license key（备选）**：RSA/Ed25519 签名 + 机器指纹二次绑定，私钥绝对不能出现在客户端代码或和签发服务同机的公网服务器上。
3. **免费层设计**：现有单机看板能力保持免费，"多台机器/多人的会话聚合到一个看板"这类本来单机做不到的能力做成付费专属。
4. 最有效的一招是"服务端校验 + 短期 token"——本地代码就算被看穿，没有服务端签发的有效 token 也用不了付费功能，比纯客户端混淆性价比高，优先级放在混淆之前。

### 阶段 4：防止逆向/反编译（**未开始**）

只在阶段 3 定下"要收费"之后才值得投入。

- Electron 路线：`asar` 打包 + `bytenode` 字节码保护 + JS 混淆（Terser/JavaScript Obfuscator）
- Tauri 路线：鉴权校验放进 Rust 编译产物
- **代码签名证书是必需品，不是加分项**：优先级要放在混淆加固之前——先解决"能不能装上"，再谈"装上后好不好破解"

### 阶段 5：容易被漏掉的其他事项（**部分完成**）

- 隐私合规：核心数据是用户在各 AI 工具里的完整会话内容，相当敏感，云端同步一旦涉及必须有隐私政策、加密传输/存储，默认"只同步元数据，会话正文留在本地" —— **未做**
- 第三方 ToS 风险：适配器读取的是官方工具的本地数据格式，非公开 API，官方升级可能随时 break —— 持续风险，无法一次性解决
- 自动更新机制（`electron-updater`） —— **未做**（依赖阶段 2 先选定 Electron/Tauri）
- 付费/使用遥测、错误上报/崩溃收集（如 Sentry） —— **未做**
- **License/EULA/隐私政策文本、README** —— **2026-08-23 部分完成**：README.md、LICENSE（专有）已补齐；EULA、隐私政策仍未做
- 定价参考：同类工具主流是 seat + usage 混合定价，具体数字要等真实验证后再定，不建议现在拍数字
- 开源与否：已在阶段 0 定为闭源

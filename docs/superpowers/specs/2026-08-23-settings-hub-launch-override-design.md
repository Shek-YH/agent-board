## 现状核查（写代码前做的真实排查）

- pi 跳转的默认实现是 `server.js` 的 `AGENT_DEFS.pi.launchCmd` 指向 `pi-launch.bat`，这个批处理用 `netstat -ano | findstr ":3210" | findstr "LISTENING"` 判断 Web UI（`http://127.0.0.1:3210`，由独立 npm 包 `@watercol/pi-web-ui` 提供，和这台机器上今天卸载重装过的 `@earendil-works/pi-coding-agent` 命令行工具是两个不同的包，没有互相影响）是否已经在跑。
- 根因：`server.js` 用 `spawn('cmd.exe', ['/c', p], {windowsHide:true, detached:true})` 调用这个批处理，**没有设置 `stdio`**（默认是 `'pipe'`）。Windows 下这种写法有个已知坑：`windowsHide` 只隐藏直接子进程（`cmd.exe`）的窗口，批处理内部通过管道调用的 `netstat.exe`/`findstr.exe` 这些控制台程序，在父进程控制台被隐藏、且 stdio 又走管道（不是显式 `ignore`）的组合下，Windows 会给这些子进程各自分配一个新控制台窗口——正好对应用户截图里那两个残留的 `findstr.exe` 窗口。
- `pi-web-ui.cmd`/`@watercol/pi-web-ui` 包本身文件完好，不是"装坏了"，是启动脚本本身的问题。
- 顶栏 quick-agent 图标、会话卡片的"跳转"按钮（`.s-jump`）、抽屉里的"跳转"按钮（`.d-jump`）三个入口全部调用同一个前端函数 `launchAgent(agent)` → `POST /api/launch-agent` → 服务端 `launchOrFocus(agent, cb)`。这意味着只需要改 `launchOrFocus` 这一处，三个入口自动全部受益，不需要分别改。

## 一、集中设置面板

### 入口

工具栏里"瀑布流设置"的图标（`btn-cols`，当前是四个小方块图标）换成一个通用的齿轮"设置"图标，`title` 从"管理瀑布流列（显示/隐藏/排序）"改成"设置"。点击后不再直接打开列管理弹窗，而是先打开一个新的"设置面板"弹窗。

### 面板内容

竖排列表，每项一个按钮，点击后关闭本面板、打开对应的子弹窗（复用现有 `closePopover()` 再开新弹窗的交互模式，和应用管理/列设置弹窗的模式一致，不引入页面路由）：

1. **瀑布流设置** → 打开现有的 `openColManager()`（逻辑不变，只是入口换了）
2. **提示音设置** → 打开"完成会话提示音"设置弹窗（见另一份设计文档）
3. **皮肤设置** → 占位符：点击直接 `toast('敬请期待')`，不打开任何弹窗
4. **模型端口设置** → 打开本文档下面第二节描述的新弹窗

## 二、pi 跳转 bug 修复

`server.js` 里 pi 的默认启动方式改成：不再依赖 `pi-launch.bat` 的批处理管道，改成 Node 原生的端口探测 + 启动逻辑：

```
① TCP 探测 127.0.0.1:3210 是否已经有服务在监听（net.connect，短超时）
   ├─ 能连上 → 直接 spawn 打开浏览器到 http://127.0.0.1:3210，结束
   └─ 连不上 ↓
② spawn 启动 pi-web-ui.cmd（stdio 显式设成 'ignore'，不再走管道，
   这是修掉窗口残留的关键——没有 stdio 管道，Windows 就不会给它分配控制台）
③ 轮询①的探测逻辑（比如每 500ms 一次，最多等 8 秒）
   ├─ 探测到端口起来了 → 打开浏览器，结束
   └─ 超时还没起来 → 照样打开浏览器（尽力而为，和原来批处理"等 6 秒后不管三七二十一直接开"的兜底行为一致，
      不无限等待卡住用户）
```

`pi-launch.bat` 修完之后不再被任何代码引用，顺手删除这个文件（不留死代码）。

这段逻辑不做成通用抽象（比如给其他 agent 也支持"web UI + 端口探测"模式）——目前只有 pi 这一个 agent 是这种"本地起一个 web 服务再开浏览器"的模式，没有第二个用例，YAGNI。

## 三、模型端口设置（自定义启动命令）

### 存储

新建 `~/.agent-board/launch-overrides.json`（即 `%USERPROFILE%\.agent-board\launch-overrides.json`），格式：

```json
{
  "pi": "\"C:\\path\\to\\某个带UI的pi启动器.exe\""
}
```

- 只在用户真的配置了某个 agent 的覆盖时，才有对应的 key
- 和现有的 `~/.agent-board/tool-paths.json`（cli 安装探测的路径覆盖）是同一套"机器级用户配置、不进 git"的思路，两个文件功能不同、互不影响，不合并成一个文件（合并会让两者的读写逻辑纠缠在一起，没有必要）

### 服务端

`launchOrFocus(agent, cb)` 开头加一步：

```
如果 launch-overrides.json 里这个 agent 有配置的覆盖命令
  → 直接 spawn 这条命令（stdio:'ignore'，不做任何"是否已运行"的检测——
    覆盖命令是用户自己指定的任意程序，没法通用地判断它"是否已经在跑"，
    交给用户自己选的程序/脚本自己处理，这里只负责"跑一下"）
  → 结束，不走下面原有的 scheme/launchCmd/focus 逻辑
否则 → 走原有逻辑（这次顺带修好的 pi 默认路径也在"原有逻辑"里）
```

新增两个 API：
- `GET /api/launch-overrides`：返回当前配置的覆盖表（给设置弹窗回显用）
- `POST /api/launch-overrides`：body 是 `{ agent, command }`（`command` 为空字符串表示清除该 agent 的覆盖），写入/删除 json 文件里对应的 key

### 前端

"模型端口设置"弹窗：每个 agent（8 个都列，不限于当前有 `launch`/`launchCmd`/`scheme` 配置的）一行，展示：
- agent 名字/图标
- 只读小字展示"默认启动方式"是什么（比如 pi 显示"默认：命令行工具直接跳转"，claude 显示"默认：claude:// 协议跳转"——纯展示性文字，不需要精确到底层字段名，给用户一个大概认知）
- 一个输入框，留空 = 用默认，填了内容 = 覆盖；输入框初始值来自 `GET /api/launch-overrides`
- 保存按钮（每行各自保存，避免用户改了一堆还没保存就关掉弹窗丢失修改；参考现有列设置弹窗"改了立即生效"的交互，这里也做成"输入框失焦或按钮点击就保存"）

## 错误处理

- 覆盖命令执行失败（比如用户填了个不存在的路径）：`spawn` 本身几乎不会同步抛错（`spawn` 是异步的，路径错误通常在子进程里体现，而不是 Node 侧抛异常），所以这里不强求"检测到执行失败并提示用户"——保持和现有 `launchCmd`/`launch` 处理方式一致（这两处现有代码目前也没做失败检测），不为覆盖命令单独造一套错误检测机制
- pi 默认路径的端口探测超时：按上面"轮询"一节描述，超时后照样打开浏览器，不额外报错阻塞用户

## 测试

- `launch-overrides.json` 的读写（有/无文件、空文件、格式错误）参考现有 `loadUserOverrides()`（`lib/detect.js`，用于 `tool-paths.json`）已经验证过的容错模式，写单测覆盖
- pi 的端口探测+启动逻辑：单测用可注入的 `net.connect`/`spawn`（同 `installAgent` 已经建立的依赖注入测试模式），覆盖"已监听直接开浏览器""未监听则启动再轮询""轮询超时后仍打开浏览器"三条路径
- `launchOrFocus` 覆盖命令优先级：单测覆盖"有覆盖走覆盖分支，不碰原逻辑"
- 人工验证：这台机器上真实点击 pi 的跳转按钮，确认不再弹出残留的 findstr 窗口、浏览器正确打开到 pi 的 Web UI；配置一个模型端口覆盖（比如随便指向一个能验证"确实被执行"的命令，如打开记事本），点跳转确认命令真的被执行

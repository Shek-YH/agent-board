# Agent Board 项目扫描调度设计

## 1. 背景

Agent Board 当前启动时会对最近 30 天的会话文件做一次扫描，运行中再依靠文件监听、目录快照校对和各 Agent adapter 的增量补扫。真正的全量扫描由手动“重新扫描”触发。

当历史项目和会话数量增多时，启动阶段的 30 天扫描会增加磁盘读取和解析压力；如果为了完整性频繁做真正的全量扫描，又会重复读取冷项目。Todo 列表的延迟问题已经暴露出同一个底层矛盾：扫描、持久化和实时请求需要彼此隔离。

## 2. 目标

1. 启动后优先让最近活跃项目和新建 Session 出现在看板中，减少首屏等待。
2. 降低冷项目在启动和常规后台校对中的扫描频率。
3. 每 6 小时自动完成一次全量一致性校验，同时保留手动全量扫描能力。
4. 保证自动扫描、手动扫描和文件监听不会并发造成重复扫描或数据竞争。
5. 普通用户无需理解“24 小时、7 天、30 天”等扫描规则，也不增加复杂配置项。
6. 扫描过程持续让出事件循环，不能阻塞 HTTP、SSE 和看板首屏。

## 3. 非目标

- 本阶段不重写各 Agent adapter 的解析逻辑。
- 本阶段不把所有扫描迁移到 Worker 线程；如果后续数据规模仍使全量解析过重，再单独评估。
- 本阶段不开放每个时间窗口的手动参数配置。
- 本阶段不改变手动全量扫描的用户入口和“保留已有卡片、重置读取偏移”的语义。

## 4. 推荐方案：智能分层 + 单一调度器

### 4.1 事实来源

项目活跃度使用两个来源的最大值：

- 已入库 Session 的 `last_seen`；
- 文件发现阶段得到的文件修改时间（`mtime`）。

这样可以覆盖两种情况：应用运行期间新建 Session，以及应用关闭期间老项目新建 Session。只看数据库中的 `last_seen` 会把第二种情况误判为冷项目。

扫描调度不为每个项目创建独立定时器，而是维护一个全局扫描队列和一个扫描锁。项目或文件只进入对应优先级队列，队列由统一调度器按时间和优先级消费。

### 4.2 启动阶段

启动顺序：

1. HTTP 服务先监听，立即允许 `/api/state`、`/api/todos` 等请求处理。
2. 轻量发现所有数据源的文件路径、`mtime`、大小和已有文件指纹，不解析历史正文。
3. 优先扫描最近 24 小时内修改的文件，以及没有可靠历史指纹的新文件。
4. 最近 1 周内活跃的项目进入后台增量校对队列，不阻塞首屏。
5. 7 天以上的项目不参加启动优先队列，等待 6 小时全量扫描或文件监听发现变化。

如果上次成功全量扫描距今已超过 6 小时，启动阶段在首屏可用后再排入一次全量扫描；不在 HTTP 监听前执行，也不与启动优先扫描并发。为了避免每次重启重复补扫，`lastFullScanAt` 必须持久化。

### 4.3 运行中策略

文件监听仍是低延迟主路径；定时扫描只作为漏事件和目录晚创建的兜底。

| 活跃度 | 默认行为 |
| --- | --- |
| 最近 24 小时 | 文件事件即时处理；高优先级增量校对 |
| 最近 1 周 | 每小时进入一次低成本增量校对候选队列 |
| 最近 1 个月 | 不做单独高频扫描，依靠文件事件和全量扫描 |
| 超过 1 个月 | 只依靠文件事件、手动扫描和 6 小时全量扫描 |

“每小时校对”应优先检查文件指纹、大小和 offset；未变化文件直接跳过，不重新解析正文。7 天以上项目不另设独立扫描定时器，避免与 6 小时全量扫描重复。

### 4.4 自动全量扫描

- 周期：每 6 小时最多成功执行一次。
- 首次启动：如果已到期，等待服务可用和启动优先扫描结束后排队执行。
- 执行条件：当前没有其它扫描；若有扫描，则将请求合并到当前或后续队列。
- 失败处理：失败不更新时间戳，记录错误并等待下一周期；不能因为失败形成紧密重试循环。
- 成功处理：只在扫描成功完成后写入 `lastFullScanAt`，并重新计算下一次截止时间。
- 手动触发：手动全量扫描拥有更高优先级；若已有自动全量扫描在执行，则复用当前任务并返回进行中状态，不启动第二个任务。
- 重启恢复：从持久化时间戳判断是否到期；停机期间错过多个周期时只补做一次，不追赶执行多次。

全量扫描仍按批次让出事件循环，并继续使用已有的幂等 `source_id`、offset 和拓扑处理逻辑。扫描结束后的持久化必须是脏数据感知的：没有实际状态变化时不重新序列化整个 `data.json`。

## 5. 调度状态与数据流

调度器至少维护以下状态：

- 当前扫描类型：`startup-recent`、`warm-reconcile`、`scheduled-full`、`manual-full`；
- 是否正在扫描；
- 是否有待执行的更高优先级请求；
- 上次成功全量扫描时间；
- 上次扫描结果、耗时、文件数、解析条数和错误信息。

状态应通过现有的扫描 SSE/健康状态能力提供给诊断使用，但不要求普通用户看到调度细节。用户手动触发时只需要看到“扫描中/已完成/失败”三种结果。

事件与定时校对发现同一个文件时，使用已有 offset、文件指纹和幂等入库逻辑去重。扫描锁只负责避免同时执行，不负责丢弃文件变化；扫描期间发生的文件事件应在结束后继续进入校对队列。

## 6. 持久化与资源控制

1. 扫描批次默认禁止触发延迟全量保存，扫描阶段只更新内存索引和读取元数据。
2. 扫描结束后只有在数据、offset 或调度状态发生变化时才保存。
3. 全量扫描不应因为“没有新消息”而重复生成 100MB 级别 JSON 快照。
4. 自动全量扫描和手动全量扫描都使用同一条执行路径，避免两个实现产生不同的数据语义。
5. 记录扫描耗时和变更量，后续可以根据真实机器数据决定是否需要 Worker 线程或 SQLite 索引。

## 7. 风险与处理

### 新 Session 在应用关闭期间产生

通过启动轻量发现阶段的文件 `mtime` 和新文件识别，将其加入最近 24 小时优先队列，不依赖已有项目记录。

### 文件监听与全量扫描重复入库

沿用现有 source-id 幂等覆盖、offset 和扫描锁；扫描完成后再次处理扫描期间发生变化的文件。

### 应用频繁重启导致全量扫描重复执行

将 `lastFullScanAt` 持久化，并以成功完成为更新时间点。启动补扫只允许补做一次。

### 历史消息被重新解析后错误变成活跃

保留现有“使用源日志时间而不是扫描时间”的状态判定规则，并增加全量重扫回归测试。

### 6 小时全量扫描随着数据增长变重

先通过扫描指标观察；如果单次扫描超过可接受阈值，再将解析工作移到 Worker 或增加持久化文件索引，不在本阶段预先引入复杂架构。

## 8. 测试与验收标准

### 单元测试

- 活跃度分层使用 `last_seen` 和文件 `mtime` 的较新值。
- 24 小时、7 天、30 天边界值正确归类。
- 自动全量扫描到期判断正确，手动扫描优先级正确。
- 扫描请求合并，不能并发启动两个扫描。
- 扫描失败不推进 `lastFullScanAt`，重启不会追赶多个周期。
- 无数据变化时不触发全量 JSON 快照保存。

### 集成测试

- 启动后 HTTP 首屏请求不等待扫描完成。
- 启动优先扫描先于后台温项目校对执行。
- 启动期间新建文件能被优先发现。
- 文件事件、每小时校对和 6 小时全量扫描同时到达时不丢数据、不重复执行。
- 手动全量扫描与自动全量扫描互斥且可复用进行中的任务。

### 验收指标

- Todo 和看板首屏请求不因启动扫描排队。
- 在同一份数据上，重启不会在 6 小时窗口内重复执行全量扫描。
- 冷项目不参与高频解析；未变化文件在每小时校对中被跳过。
- 全量扫描仍能补齐应用离线期间产生的 Session。
- 全量测试通过，且保留当前已有的扫描、状态和拓扑回归测试。

## 9. 分阶段实施

1. 抽取扫描调度器，统一启动、后台和手动扫描请求，先建立互斥、合并和状态持久化。
2. 将启动默认扫描改为“最近 24 小时优先 + 最近 7 天后台队列”。
3. 加入每小时温项目校对和每 6 小时自动全量扫描。
4. 增加脏数据感知持久化、扫描指标和回归测试。
5. 用真实运行数据复核 CPU、磁盘读取、扫描耗时；若仍有瓶颈，再单独设计 Worker/索引优化。
